Token X-ray

A loss function is an equation. A trainer is a program. These are radiographs of the program: the gradient weight every token received, measured by running each library's own training loop on a tracer model.

Every token gets a vote

Most language-model trainers optimise the average loss over the tokens in a batch. With N target tokens, each one's gradient is scaled by exactly the same amount:

On a radiograph of one training step, where each cell is a token and its brightness is the weight it received, that is an even, featureless grey. Featureless is healthy. Rows are sequences; their length is the number of tokens they contribute.

Splitting the batch should change nothing

Large batches rarely fit in memory, so trainers split them into micro-batches and add up the gradients. Done right, the radiograph cannot tell the difference.

  1. The transformers Trainer, four accumulation steps

    Twelve sequences, four micro-batches of three, through the library's own Trainer loop. Every token lands within 2×10−7 of its intended weight, the instrument's precision floor. This is a real run.

  2. Average each micro-batch first, then average the averages

    Micro-batches with few tokens now count as much as micro-batches with many, so their tokens get louder. The bands are the bug. This is the transformers Trainer as released before its October 2024 fix, run on the same twelve sequences in a separate environment: a real run, not a reconstruction.

  3. Split across two processes, average on each

    The same twelve sequences on two data-parallel ranks, through the Trainer's own loop under torchrun. With average_tokens_across_devices=False each rank averages its own tokens and DDP then averages the ranks, so the rank holding fewer tokens gets louder. The default shares the token count across ranks; measured that way on the same split, the weights are flat again (the caption gives the deviation). This is a real run.

  4. Keep only the first micro-batch

    Three quarters of the batch goes dark and nothing crashes. This plate emulates, in plain PyTorch, the effect on gradients of a bug in DeepSpeed's ZeRO-1/2 CPU-offload path, which its finders trace to PR #6550 (September 2024) and to a fix in PR #7967 (April 2026). The real bug sits after backward, in the optimizer's gradient buffer, where this X-ray cannot see it. It is one of two silent bugs that weakened the SFT baselines of several recent mixed-policy RL papers, found by Limozin et al. (2026).

Some objectives tilt the vote on purpose

Reinforcement learning on language models scores whole answers. Six answers to one prompt, three right and three wrong, and three ways to turn their rewards into token weights. Brightness is how hard each token is pushed; the label says which way.

Small settings rewrite the objective

Each is a setting that quietly changes which tokens count, and each shows up on the film. All three are real runs of the library as configured.

Documents that read each other

Packing several documents into one row saves padding, as long as they cannot see each other. Here, one document at a time is given a loss, and every other document should receive exactly zero gradient. Each film is a grid: the row is the document with the loss, the column is the document that received gradient. Whether a leak exists does not depend on the model; how large it is does, and these sizes are for this untrained probe.

A known issue: packed documents and use_cache

transformers detects packed documents from position_ids only when no attention_mask is passed and no cache object exists. Most model configs default to use_cache=True, which creates one even in training mode. A hand-written loop that feeds packed position_ids without use_cache=False lets documents attend to each other, with no warning. Loops with gradient checkpointing are unaffected: it turns the cache off. So is the Trainer, which sets the flag from its arguments. Measured on .

It is already reported in transformers#50419. A maintainer first replied that a cache should not be used during training and suggested documenting that requirement, then noted that use_cache defaults to true and linked the issue to a proposed fix. Fixes are proposed in #50190 and #50421. Until one lands, pass use_cache=False when you train on packed sequences.

What preference and RL trainers apply

The same X-ray runs through TRL's trainers. These objectives are signed: a bright cell is a token the step pushes hard, up for an answer the loss favours and down for the others. The row label says which way. A dark cell received no gradient at all.

The completions here are scripted tracer sequences with fixed rewards, so the trainer's own code does the slicing, masking, scoring and reduction while every number stays checkable against its equation. The equations hold for any model; the sizes they produce here (the DPO margin, GRPO's ratios and clipping) depend on the model's state, so they describe this untrained probe.

X-ray your own training step

Write a function that batches the probe's sequences exactly as your trainer does and runs one backward pass. Token X-ray swaps in a tiny model whose every token is a unique tracer and reads back the weight each one received. 

from token_xray import xray

def my_step(model, sequences):
    batch = my_collator(sequences)       # your code
    loss = my_loss(model, batch)         # your code
    loss.backward()

report = xray(my_step, lengths=[5, 9, 3, 12, 7, 4, 10, 6])
report.assert_token_mean()               # fails loudly if any token is off

Every check in the package is mutation-tested. scripts/mutate.py plants 43 faults, one at a time: 35 in the instrument itself (readout, recorder, probe, closed forms, leak harness, runners, data-parallel launchers) and 8 realistic bugs injected into transformers and TRL. Every fault is caught, and each of the 52 tests catches at least one; it runs on every push to main.

How these films were made

Real runs drive the installed library's own training loop, loss and collators on the tracer probe. Each changes these things from the defaults: the sample order is fixed (a sequential sampler; shuffled order is tested separately), gradient clipping is off (max_grad_norm=0), bf16 is off, GRPO's completions are scripted (model.generate returns fixed tracer sequences), and the training step is wrapped only to record gradients. Emulations reproduce, in plain PyTorch, the documented mechanism of a bug in code we cannot run here, and are labelled on the film's edge. The hero runs transformers 4.45.2 in a separate environment; everything else is measured with . Weights are shown as w·N, so a correct global token mean is 1.0; the instrument's precision floor is about 2×10−7.

The readout sees the gradient at the embedding output during backward (for data-parallel runs, the embedding's parameter gradient after the all-reduce). It shows how the loss weights each token, before gradient clipping and the optimizer; bugs that live in the optimizer step are outside its view.

The probe is a two-layer LLaMA with untied embeddings. In weight mode its attention output is zeroed, so each token's loss depends only on its own embedding and the gradient the stack produces at token i is wi times that token's unit gradient. The readout recovers wi and a cosine that drops below 1 when the change is not a pure rescaling. The probe is untrained, so its predictions are near-uniform: numbers that depend on the model's state (label smoothing's cosine, the DPO margin, GRPO's ratios, the size of a leak) describe this probe, not a trained model.

Preference and RL trainers repeat the prompt in every row, so its last token predicts a different first token in each answer. Each of those weights is solved for separately, with the solve's condition number and the unexplained remainder of the gradient reported with the measurement. Gradient reaching padding is collected rather than dropped, and is zero in every run. TRL runs pass bf16=False: TRL's configs default to bf16 mixed precision, which on this probe scatters individual SFT weights by up to without re-weighting any sequence: every sequence's mean weight stays within bf16's unit roundoff, 2−8 (in GRPO it could also move tokens across the clip boundary).
